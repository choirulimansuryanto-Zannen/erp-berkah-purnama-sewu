## Implementation notes (2026-08-26, round 40 — Laku column defaults to Terjual (Sistem) until Ambil/Sisa are actually counted)

Small but easy-to-get-wrong UX fix in `StockTable` (`stock-table.tsx`), shared by Table 1 on Laporan Harian: Laku was always computed as `Ambil − Sisa`, and since those two fields start blank (read as 0), every row showed Laku = 0 before the cashier had counted anything — misleading, since the system already knows how much sold (Terjual/Sistem) and Laku is *supposed to* reconcile against that.

- Changed the default: while both Ambil and Sisa are still untouched (blank strings, not yet even "0"), Laku now mirrors Terjual (Sistem) instead of computing to 0 — and Total Omset at the bottom follows along automatically since it's derived from Laku × harga per row. The instant either field gets a real value typed in, Laku switches to the actual `Ambil − Sisa` computation as before.
- Deliberately keyed off the *string* being non-empty (`ambilStr !== "" || sisaStr !== ""`), not the numeric value being non-zero — a cashier typing `0` into Sisa (a real, deliberate count) must switch the row into "counted" mode immediately, not be treated the same as "not yet touched."
- Scoped entirely to the live pre-submission entry table — `StockTable` is only ever rendered before a report is submitted (the submitted state shows a locked message instead), so nothing about historical `DailyReportStockLine` display needed touching.
- Verified live across all 16 tracked items on real session data: every row's Laku matched its Terjual (Sistem) value exactly by default (including non-zero ones — Kebab Jumbo 9/9, Cheese 10/10), then confirmed switching to 45 after typing Ambil=50/Sisa=5, then reverting back to the Terjual-matching default after clearing both fields. ## Implementation notes (2026-08-11, round 15 — POS identity mismatch + @db.Date timezone bug)

Stakeholder reported that after returning to the cashier screen, the pramuniaga name and shift shown didn't match what was picked at check-in.

- **Immediate fix**: `src/app/(dashboard)/layout.tsx` (the header shared by every page, including POS) was still sourcing `userName`/`shiftLabel` from the *login account's* static `user.name`/`user.shift`, not from the open session's `pramuniagaRoster`/`shift` set at check-in (round 10 introduced that split but never updated the header). - **Root cause underneath it, found while verifying the fix live**: a fresh check-in on real "today" collided with/landed on the wrong date entirely. Traced to `startOfToday()` (round 14) — local midnight — being written directly into `@db.Date` columns. Postgres `DATE` has no timezone; Prisma serializes a JS `Date` to one by taking its **UTC** calendar date. In this system's timezone (Asia/Bangkok, UTC+7), local midnight is still the *previous* UTC day, so every write silently landed one calendar day early. This affected `AttendanceRecord.date` (check-in upsert key, team-attendance-today query, HRGA compliance window), `OperationalChecklistSubmission.date`, and the attendance history date-picker's lookup — plus, confirmed retroactively, the round-14 sample history seed itself, which is why every seeded row's stored `date` was one day behind its actual `timeIn`.
- **Fix**: added `toDateOnlyKey(d)` to `src/lib/session-date-helpers.ts` — builds a `Date` from `d`'s *local* Y/M/D but at *UTC* midnight, which is what actually round-trips correctly through a `@db.Date` column. Routed every place that writes or exact/range-matches a `@db.Date` column through it: `getSessionDate()`'s fallback, check-in's upsert key (kept `startOfToday()` separately for the LATE-cutoff time calculation, which does need a true local-midnight instant), the attendance page's team-view and history-picker queries, inventory's stock-summary query, HRGA's compliance window, finance's expense-by-category range, and `reports.ts`'s expense-date range (which now trusts the already-normalized `sessionDate` instead of re-deriving day boundaries with local `setHours`). Left every `DateTime`-column instant comparison (`Transaction.createdAt`, `getSessionTimeRange`) untouched — those need the true local-midnight instant, not a date-only key, and were never broken.
- **Data repair**: corrected the round-14 seed's 6 historical `AttendanceRecord` rows and their 24 `OperationalChecklistSubmission` rows by shifting `date` forward one day each (verified against each row's own `timeIn` before touching anything); deleted one stray open/uncommitted session that was a leftover artifact of an earlier failed verification attempt, not real seed data.
